# Design: Weekly AI Summary on the Dashboard (US-11)

**Date:** 2026-07-03
**Issue:** [#24 (US-11)](https://github.com/AET-DevOps26/team-99-downtime/issues/24)

---

## Summary

A short plain-language summary of the user's spending week, generated by the
genai-service and shown in a dashboard widget. Generated two ways:

- **Weekly scheduler** — a cron job regenerates every active user's summary once
  a week (Sunday evening), so the dashboard shows a fresh summary each week.
- **Manual trigger** — the widget's "Generate now" / regenerate button, so a
  user (or a demo) never has to wait for Sunday.

Before the first summary exists the widget shows an empty state; weeks with too
little data produce **no** summary rather than a misleading one.

---

## Data Flow

### Manual trigger (dashboard button)

```
Client → GET /api/transactions/weekly-report   → transaction-service (user JWT)
                                                   → this week's transactions +
                                                     last week's totals
Client → POST /api/genai/summarize (report)    → genai-service (user JWT)
                                                   → LLM turns numbers into 2-3
                                                     sentences
                                                   → upsert into genai_db
Client → GET /api/genai/summarize/latest       → genai-service (user JWT)
```

### Weekly scheduler

```
transaction-service @Scheduled (Sun 20:00 Europe/Berlin, summary.cron)
  → distinct userIds with transactions in the last 2 weeks (own DB)
  → per user: build the same WeeklyReport from its own DB
  → POST /internal/summarize {userId, ...report} → genai-service
                                                     → generate + upsert
```

### Why the caller supplies the data (and why /internal exists)

Every user-facing endpoint validates a per-user JWT and there are no service
accounts (see `AUTHENTICATION.md`). A cron acts for many users at once, so no
user token exists to forward — the scheduler therefore lives in
**transaction-service, the owner of the transaction data**, reads its own
database, and pushes the numbers to genai. The genai-service never fetches data
itself; both paths deliver the identical `WeeklyReport` payload, so summaries
are the same no matter who triggered them.

`POST /internal/summarize` carries the target `userId` in the body and is
deliberately **not** JWT-protected. Trust is the network boundary: the gateway
(Caddy / ingress) routes only `/api/genai*` to the service, so `/internal/*` is
unreachable from outside the compose/cluster network. The route is excluded
from the OpenAPI spec.

### Week semantics

- `weekStart` = Monday of the current ISO week.
- `thisWeek` = the user's transactions in `[weekStart, weekStart+6]`.
- `lastWeek` = total + count over `[weekStart-7, weekStart-1]`.
- One summary row per `(userId, weekStart)` — regenerating overwrites
  (`ON CONFLICT DO UPDATE`), the dashboard reads the row with the newest week.

## Backend

### genai-service (FastAPI)

New module `summarize.py` (prompt + rules), `store.py` (asyncpg), `llm.py`
(chat call extracted from `categorize.py` so both features share one seam).

| Method | Path                          | Auth     | Notes                                                                   |
| ------ | ----------------------------- | -------- | ----------------------------------------------------------------------- |
| POST   | `/api/genai/summarize`        | user JWT | body = WeeklyReport; generates, upserts, returns the summary            |
| GET    | `/api/genai/summarize/latest` | user JWT | newest stored summary; `404 NO_SUMMARY` before the first one            |
| POST   | `/internal/summarize`         | network  | scheduler path; body additionally carries `userId`; hidden from OpenAPI |

**Contracts**

- `422 NOT_ENOUGH_DATA` — fewer than `MIN_TRANSACTIONS` (3) transactions this
  week; nothing is stored (acceptance criterion: no misleading summaries).
- `502 LLM_UNAVAILABLE` — gateway unreachable / unusable reply (mirrors
  categorize).
- `503 SUMMARY_STORE_UNAVAILABLE` — no `DATABASE_URL` configured.

**Prompt** — deterministic build (tested byte-for-byte): system prompt fixes
style (2–3 plain sentences, ≤ 60 words, concrete numbers, compare to last week
only when `last_week.count > 0`, no advice); user message is the payload as
JSON. `temperature: 0`.

**Persistence** — `weekly_summaries(user_id, week_start, summary, generated_at)`
in the new `genai_db`, unique on `(user_id, week_start)`, schema created on
startup. `DATABASE_URL` is optional so bare local runs and unit tests need no
Postgres.

### transaction-service (additions)

| Method | Path                              | Notes                                                   |
| ------ | --------------------------------- | ------------------------------------------------------- |
| GET    | `/api/transactions/weekly-report` | the WeeklyReport for the calling user — the manual path |

- `WeeklyReport { weekStart, thisWeek: [{date, amount, currency, description}], lastWeek: {total, count} }`.
  Transactions carry no category _names_ (those live in budget-service), so the
  report sends descriptions — enough signal for the LLM to name themes.
- `WeeklySummaryJob` — `@Scheduled(cron = ${summary.cron:0 0 20 * * SUN}, zone = ${summary.zone:Europe/Berlin})`;
  posts each active user's report via `SummaryClient` to `/internal/summarize`;
  one failing user never blocks the rest; genai's 422 counts as "skipped".
  Override `SUMMARY_CRON` (e.g. `0 */2 * * * *`) to watch the job fire in a demo.
- Repository: `findByUserIdAndDateBetweenOrderByDateAsc`, `findActiveUserIds(since)`.

### Infrastructure

- `genai_db` added to `infra/postgres/init/01-create-databases.sql` (dev),
  `k8s/helm/t99-app/files/init-databases.sql` (cluster).
- genai-service gets `DATABASE_URL` + postgres/db-init `depends_on` in both
  compose files; in Helm, the URL is assembled in the deployment from the
  `t99-db-credentials` secret.
- ⚠️ K8s init scripts run only on a **fresh** volume — an existing cluster needs
  a one-off `CREATE DATABASE genai_db;` (compose runs db-init on every up).

## Frontend

**`features/summary/`** (new feature folder)

- `api/summaryApi.ts` — `getLatestSummary()` (404 → `null`), `generateSummary()`
  (weekly-report → POST summarize; 422 → `null`)
- `hooks/useWeeklySummary.ts` — load on mount; exposes
  `{ summary, loading, error, generating, generate }`; toasts on
  not-enough-data / failure
- `ui/WeeklySummaryCard.tsx` — violet-accented card: summary text +
  "Week of … · Updated …" meta + regenerate button; loading skeleton; error
  state; empty state with "Generate now"

**`DashboardPage`** — the card spans the full width above the
RecentTransactions / BudgetBars grid.

## Tests

- **genai-service** — deterministic prompt (golden messages), not-enough-data
  stores nothing, upsert overwrites, latest 404→200, internal route, 401s,
  502/503 mapping (LLM + store stubbed, offline).
- **transaction-service** — scheduler integration test (seeded H2 → job → captured
  payload per active user; dormant users skipped; one failure doesn't block),
  week-window bucketing with fixed dates, weekly-report endpoint flow test.
- **client** — WeeklySummaryCard states (summary/meta, empty + generate, loading,
  error, regenerate), DashboardPage wiring.

---

## Out of scope

- Per-category breakdowns in the summary (needs category names from
  budget-service; descriptions already carry the signal).
- Summary history view (only the latest is shown; older weeks stay in the DB).
- Email/push delivery of summaries.
